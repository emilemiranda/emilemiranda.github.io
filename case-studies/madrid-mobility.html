Mobility & Accessibility · Case Study 01/05

Madrid Mobility Accessibility

A reproducible GIS workflow that combines BiciMAD stations and available usage context with EMT bus stops and routes to compare mobility-service coverage across Madrid neighborhoods and districts.

Python GeoPandas Madrid Open Data EMT BiciMAD GeoJSON
All projects Explore Live Map

Project overview

This project turns transport point and route datasets into neighborhood-level measures that can be compared across Madrid. It combines BiciMAD stations and usage context where available, EMT bus stops and routes, and official administrative boundaries for neighborhoods and districts.

Project question: How are bike-share and bus access points distributed across Madrid neighborhoods, and where do the chosen access rules indicate potential service gaps?

The workflow is designed as a reproducible analytical product: inputs are downloaded, cleaned, aligned spatially, summarized, and exported so a reviewer can inspect both the maps and the underlying tables.

Data and sources

  • Madrid Open Data: official city open-data inputs documented in the project source registry.
  • EMT: bus stops and route data used for the mobility coverage analysis.
  • BiciMAD: station information and usage context where the available history fields support it.
  • Administrative geography: official district and neighborhood boundaries used to summarize results.
Documented data snapshot: the project README states that the official datasets used for the documented run were retrieved on 18 June 2026 . Record individual retrieval times and source versions in data_sources.md when regenerating results.

The supplied project notes do not identify a fixed walking-distance threshold. The actual configured buffer distance should be recorded beside any published score or map legend rather than inferred from this narrative.

Method and workflow

  1. Acquire the source data. Download the relevant official city and EMT open-data inputs.
  2. Clean and standardize. Validate geometries, normalize fields, standardize the coordinate reference system (CRS), and create stable identifiers.
  3. Build access zones. Create service-area buffers around BiciMAD stations and EMT stops using the project’s configured distance assumptions.
  4. Overlay with administrative units. Intersect service zones with neighborhood and district polygons.
  5. Calculate indicators. Derive coverage measures and classify potential service gaps using the documented rules.
  6. Export results. Save summary tables, GeoJSON layers, maps, and charts for review and reuse.

What the outputs measure

The project defines a set of comparable, neighborhood-level indicators rather than relying only on point maps of stops and stations.

  • Area coverage: percentage of each neighborhood area within the configured walking-distance buffers of access points.
  • Service inventory: number of EMT stops and number of BiciMAD stations in each neighborhood.
  • Route presence: whether EMT route geometry is present within a neighborhood.
  • Usage context: usage-weighted BiciMAD activity where the available history data contains suitable fields.

These metrics support comparison of service patterns, but they do not by themselves prove that a resident can reach a stop in a given travel time. The project brief does not provide the actual score values or highest-/lowest-ranked neighborhoods, so this page does not name specific winners or gaps without a verified output table.

Outputs and deliverables

  • Neighborhood accessibility scores.
  • District summary statistics.
  • Service-gap summaries.
  • GeoJSON layers suitable for mapping.
  • PNG maps and charts, with planned figure names access_map.png and gap_chart.png under results/figures/ .

The repository is organized around a repeatable four-step script sequence:

  1. scripts/01_download_data.py
  2. scripts/02_clean_data.py
  3. scripts/03_spatial_analysis.py
  4. scripts/04_export_results.py

Assumptions and limitations

  • Buffer coverage is a proxy. The project documentation explicitly notes that buffer-based access is not a full pedestrian street-network travel model.
  • Usage data is conditional. Usage-weighted BiciMAD activity depends on which fields are available and complete in the history file.
  • Spatial presence is not service quality. Stop/station counts and route presence do not by themselves measure service frequency, capacity, operating hours, or actual travel time.
  • Data is time-dependent. The documented run uses a data snapshot retrieved on 18 June 2026; results may change as source portals are updated.

Next steps

  • Publish the exact configured buffer distances and the definitions of every score.
  • Use network-based pedestrian travel areas to complement the buffer proxy.
  • Extend the equity analysis to census-section scale where source data permits.
  • Explore time-of-day or monthly BiciMAD usage patterns where the source fields support them.
  • Add the verified access map and gap chart from the exported results folder.
